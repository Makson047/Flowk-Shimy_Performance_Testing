## Три чіткі фази деградації

### 🟡 Фаза 1 — повільне обслуговування (t≈30 с, ≈45 VU)

Сервер відповідає, але повільніше за SLA. Латенція росте лінійно з VU: на кожні +50 VU додається ~3-4 с до p95. Помилок немає. Класичний паттерн «черга росте швидше за обробку».

### 🟠 Фаза 2 — поява помилок (t≈80 с, ≈469 VU) — точка фактичного зламу

Latency впирається в плато ~30 секунд — це характерна цифра **server-side або LB timeout** (типовий `proxy_read_timeout` у Nginx). Як тільки запит виходить за timeout — він повертається 504/502 Gateway Timeout. Перші 5xx+network errors з'являються рівно в момент, коли latency впирається в стелю.

### 🔴 Фаза 3 — масовий збій (t≈110 с, ≈719 VU)

Більше половини запитів падає. На 1000 VU — стабільно 60-80% failure rate; p99 ~40 секунд. Сервер тримає TCP-конект, але обробити запит не встигає → LB обриває.

## Latency-плато на ~30-40 секундах

Починаючи з t=120 с (1000 VU) і до кінця тесту **p95 не зростає необмежено** — стабілізується в коридорі **34-40 с**. Це **не межа сервера**, а **межа LB / proxy timeout-у**:

- Запити, що встигають за ~30 с → 200 OK
- Запити, що не встигають → 504 → 5xx

Реальний бекенд може обробляти запит ще довше — ми цього не бачимо, бо LB обриває раніше.

## Action items для бекенд-команди

### Найважливіше повідомлення

> **Сервер не падає від кількості з'єднань — сервер повільний на одиничному запиті.** На 200 VU при базовій latency 0.6 с теоретично можна було б отримати ~330 RPS. У нас 12 RPS — у 27 разів менше. Це означає, що bottleneck не в кількості з'єднань, а **всередині обробки одного запиту** — найімовірніше у DB або coniection pool.

### Що перевірити (від найімовірнішого)

1. **Postgres geo-search query plan для `/feed/`**
   - Чи є GIST/GIN індекс на `(latitude, longitude)` або PostGIS-геометрії?
   - Профіль виконання під навантаженням (slow query log)
   - Базова latency 600 мс **навіть на 0 VU** натякає на повільний/неоптимізований запит.

2. **Server-side timeout = ~30 секунд**
   - Усі обриви відбуваються рівно на 30-40 с
   - Nginx/LB: `proxy_read_timeout`, `proxy_connect_timeout`, idle timeout
   - Application server: request timeout

3. **Connection / worker pool starvation**
   - DB connection pool: розмір, скільки в use, queue size
   - API server workers: uvicorn/gunicorn worker count, Node.js event loop utilisation
   - Якщо pool=20, а навантажень 200 — кожен запит чекає у черзі за конектом

### Метрики для паралельного запуску

При наступному стрес-тесті попросити девопса/бекенд дивитись у режимі реального часу:

- **DB connection pool**: in-use vs available, queue size, чи є `pool exhausted`
- **Slow query log Postgres**: запити > 1 с протягом тесту
- **API server worker utilisation**
- **CPU / memory утилізація** контейнера API
- **Latency на Postgres-стороні** (через APM, якщо є)

Якщо paralelno з тестом DB pool буде показувати «100% used, queue 200+» — bottleneck знайдено.

## Наступні кроки

1. **Локалізувати точку перегину**: запустити кастомний прогон зі stages `[10→30→50→75→100 VU]`, щоб точно знайти, на якому VU p95 пробиває 1 секунду. Зараз ми знаємо тільки гранули: 10 VU = 0.5 с, 86 VU = 4.6 с.
2. **Запустити повторний stress після оптимізацій бекенду** — щоб виміряти, наскільки змінилися цифри.
3. **Розглянути cache layer перед `/feed/`**: відповіді геозалежні, але можна кешувати на 15-30 секунд per (lat, lon, radius) bucket — це різко знизить навантаження на DB.
