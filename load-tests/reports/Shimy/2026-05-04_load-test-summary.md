## Feed REST — детальний розбір

### Зведена таблиця

| Метрика | smoke 10 VU | load 200 VU | stress 1000 VU |
|---|---|---|---|
| RPS | 5.2 | 12.1 | 24.3 |
| p50 latency | 285 ms | 13 610 ms | 32 170 ms |
| **p95 latency** | **509 ms** | **15 637 ms** | **37 907 ms** |
| p99 latency | n/a | 16 463 ms | 39 573 ms |
| Max latency | 721 ms | 25 548 ms | 41 413 ms |
| Failed rate | 0% | 0% | **58%** |
| 5xx errors | 0 | 0 | 5 157 |
| Network errors | 0 | 0 | 201 |

### Інтерпретація

1. **RPS майже не зростає при 5× збільшенні VU** (12.1 → 24.3 при 200 → 1000 VU). Це bottleneck на сервері: апка обробляє максимум ≈25 запитів feed/сек, незалежно від кількості клієнтів у черзі.
2. **На 200 VU помилок немає — лише повільність.** TCP-конект приймається, запит обробляється, але відповідь приходить через 15 секунд. Найімовірніша причина (треба підтвердити з бекенд-командою): bottleneck у геопошуку (DB query / index), DB connection pool starvation або обмежений worker thread count.
3. **На 1000 VU 58% запитів повертають 5xx** — сервер не встигає відповідати в timeout window, бекенд / load balancer обриває з'єднання.

### Точка перегину

Знаємо тільки гранули:

- ✅ 10 VU — повністю ОК (p95 510 ms)
- ❌ 200 VU — катастрофа (p95 15 600 ms, у 30× гірше)
- 💀 1000 VU — масові збої

Точка перегину — десь між **10 і 200 VU**, ймовірно 50–100 VU. Треба окремий цільовий прогон щоб локалізувати.

### Send-режим (chat.send → chat.message peer round-trip)

|---|---|---|
| Sessions OK | 68 | 50 |
| Handshake failures | 0 | 0 |
| Закриття 4409 (duplicate) | 0 | 0 |
| Messages sent | 5 711 | 13 292 |
| Messages received | 5 597 (98%) | 13 183 (99%) |
| **Chat RTT p50** | 160 ms | 160 ms |
| **Chat RTT p95** | 245 ms | 245 ms |

**RTT абсолютно ідентичний між load і stress** — навіть за 5-хв сесій під 50 паралельних з'єднань. Це означає, що для WS-сервера 50 одночасних юзерів — легке навантаження.

### Чого ми НЕ знаємо

Реальної стелі WS не побачили — вона десь вище 50 VU, але туди ми не можемо потрапити з поточним пулом. Щоб виміряти стелю чату, треба **збільшити пул тестових юзерів до 200+** і повторити stress.

## Рекомендації

### 🔴 Для feed REST (терміново)

1. **Запитати у бекенд-команди про поведінку під 200 VU**:
   - Розмір DB connection pool
   - Профіль query плану `/feed/` (geo-search) — чи є GIST/GIN індекс на координатах?
   - Worker thread count на API-сервері
   - Cache layer перед DB?

2. **Локалізувати точку перегину**: окремий прогон з кастомними `target: 50` і `target: 100` поетапно — щоб знайти конкретний VU, де p95 пробиває 1 секунду.

3. **Розглянути кешування**: feed-відповіді геозалежні, але їх можна кешувати на 15–30 секунд per (lat, lon, radius) bucket — це різко знизить навантаження на DB.

### 🟢 Для chat WebSocket

Чат **готовий до реального трафіку до 50 паралельних юзерів** — підтверджено. Якщо очікуваний пік прод-навантаження вище, потрібен окремий round тестування з розширеним пулом юзерів.

### 🛠 Для процесу тестування

- **SLA пороги в feed-тесті** (`p95<800`, `p99<1500`) — узяті як baseline з Flowk. Тепер у нас є реальні цифри: smoke = p95 510 мс. Варто **скоригувати порог до p95<1500** для load на dev — більш реалістично, ніж 800.
- **Розширити пул юзерів** — поточних 50 недостатньо для тестування реальної стелі WS. Якщо адмінка може створити ще 150 — stress-тест стане осмисленим для чату.
