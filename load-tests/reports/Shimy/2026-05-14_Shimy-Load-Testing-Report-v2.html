Shimy Load Testing Report — v2 (after backend fix)

Bottom line: the current performance is sufficient for an MVP launch. The backend fix delivered a measurable improvement — the feed is 15–30% faster, the chat 25–32% faster, and the feed now comfortably serves up to ~160 simultaneous feed requests before slowing down. Crucially, “160 simultaneous requests” in the test is far more aggressive than real usage: real users don’t all refresh the feed in the same second, so in practice the app supports several hundred to ~1 000+ concurrent active users at this performance level. That is enough for MVP. As the user base grows, scaling up server capacity is recommended to keep the experience fast, but it is not a launch blocker. Chat is fully production-ready and now even faster.

What this means in user terms (updated)

The feed serves ~160 simultaneous requests within ~5 seconds — our reference point for "acceptable". Below that it is fast; well above it, it slows down. But "160 simultaneous requests" is a stress-test figure, not a real-user figure — the next section explains why the real capacity is far higher.

Test users vs real users — why the app supports far more than the numbers suggest

Key context for interpreting every number in this report. The load test is deliberately far more aggressive than real human behaviour. The “160 concurrent users” limit is not “160 people using the app” — it is “160 feed requests being processed in the very same moment”. In reality users never do that.

Why the test is more aggressive than reality

  • In the test, each simulated user fires a new feed request roughly every ~7 seconds, non-stop, for the entire run.
  • A real user of a dating app opens the feed, then scrolls and looks at profiles for 30–60+ seconds before the next refresh — and often just looks once and closes the app.
  • So one test "user" generates the server load of roughly 6–8 real users.

Translating the test result into real audience size

Test (k6)Real users (dating-app behaviour)
How often the feed is requestedevery ~7 s, continuouslyevery ~45–60 s during an active session
Server load per "user"1×~⅙–⅛ of a test user
Reference comfort point~160 simultaneous requests (p95 ≈ 5 s)≈ several hundred to ~1 000+ concurrent active users

In other words: the same server load that the test reaches with 160 aggressive simulated users would, in production, only be generated by roughly 1 000+ real people actively using the app at the same moment. For an MVP launch this is comfortably sufficient — a new dating app is very unlikely to have 1 000 people simultaneously refreshing their feed in the same few seconds on day one.

This is an estimate, intentionally conservative. The exact multiplier depends on real user behaviour, which we will only know after launch. The recommendation is therefore: ship the MVP now, monitor real traffic, and scale the server proactively as the audience grows.

New behaviour to confirm with the backend team

The number of dropped connections (TCP connection reset by peer) under stress jumped 3× — from 201 to 648. Meanwhile classic server errors (5xx) went down.

Stress zoneDropped connections — Run #1Run #2
Up to 500 users00
500–700 users1657
700–1 000 users71252
Total201648

Most likely explanation (to verify): the fix added fail-fast / overload-protection. Previously the server held an overloaded request for ~30 seconds and then returned a 504; now it cuts the connection quickly. For the user this is actually better (an error in ~5 s instead of a 30-s spinner). The lower total failure rate and improved latency support this benign reading — but the backend team should confirm it was intentional.

One question for the backend team: “Was fail-fast / overload protection added to the feed endpoint? We now see many TCP resets at the start of the error zone, where the server previously held connections for 30 s. Intentional?”

Verdict on the fix

  • 🟢 The fix is beneficial and should stay in production. Every measured metric improved or stayed flat; none regressed in a way that hurts users.
  • 🟢 It addressed the per-request cost — base latency dropped ~17% (≈600 ms → ≈500 ms), which is why the server now serves more users before degrading.
  • 🟢 Performance is sufficient for the MVP. Translated into real-user behaviour, the app comfortably supports an MVP-scale audience (≈ 1 000+ concurrent active users).
  • 🟡 The architectural ceiling is unchanged (load-balancer timeout ~30 s + limited parallel processing). This is not an MVP problem, but it will need attention as the app scales beyond MVP traffic — a planned growth investment, not a blocker.

Recommendations & Next Steps

Not blocking — MVP can launch now

None of the items below block the MVP launch. They are improvements and growth investments.

Post-launch growth investment (recommended as audience grows)

  1. Increase server capacity. A larger / scaled-out backend would directly push the comfort point well past the current ~160-request mark, keeping the feed fast as the user base grows. This is the single highest-leverage growth investment.
  2. Continue feed optimization. The fix proved the approach works. Next targets: drive base latency from ~500 ms toward 50–100 ms (geo-search query, indexing, caching), and raise parallel-processing / DB connection pool limits.
  3. Monitor real production traffic after launch — this tells us the real test-to-real-user multiplier and when a capacity upgrade actually becomes necessary.

Short-term housekeeping

  1. Confirm the new connection-reset behaviour with the backend team (intentional fail-fast vs. accidental pool/timeout change).
  2. Expand the test-user pool to 200+ to probe the true chat ceiling (still only proven to 50).
  3. Agree on business-defined SLA targets. Current thresholds are baseline values; once product owners set the user-facing SLA, they can be wired into CI to catch regressions automatically.
  4. Re-run this exact comparison after future optimizations — the harness produces an automatic before/after diff, so each round is cheap to measure.

Glossary (for non-technical readers)

TermMeaning
Concurrent userA user with the app open, acting in parallel with others. Not “everyone clicking the same button at the same instant”.
Latency / response timeHow long the user waits between an action and seeing a result.
p95 latencyThe wait time experienced by 95% of users — only 5% wait longer. The standard “worst typical case” metric.
5xx errorsServer-side failures — the user sees a “Something went wrong” / “Failed to load” message.
Dropped connection (TCP reset)The server abruptly closes the connection mid-request. The user sees an instant failure rather than a long wait.
Round-trip time (RTT)For chat: time between one user sending a message and the other user's device receiving it.
Smoke / load / stressTest profiles of increasing intensity. Smoke = “does it work?”. Load = “fast enough under expected demand?”. Stress = “where does it break?”.
